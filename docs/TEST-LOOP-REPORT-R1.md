## 2. 缺陷清单（按级别）

### 🔴 BUG-01【P0】悬赏方案被驳回后，认领人彻底死锁

**复现路径**（真实 UI 已跑通，截图 `tmp/L6-bounty-deadlock.png`）
```
员工认领 B01 → 提交方案（status=SUBMITTED）
→ 组织者在/admin/bounty 点「驳 回」，理由≥10 字
→ status 变为 REJECTED
→ 切回认领人进入 /bounty/B01 → 【页面无任何操作按钮】
```

**现象**：驳回后认领人页面只剩导航与「返回悬赏榜」，**提交方案 / 修改方案 / 补充资料 三个入口全部消失**，悬赏永久卡死。

**根因假设**（已定位到行）
1. 方案驳回复用发布审核的同一个 `reject()`（`src/pages/b/BountyReview.tsx:51-60`），把 status 置为 `REJECTED`；
2. 但「提交方案」的显示条件是 `status === 'CLAIMED' && claimant === me`（`useBountyBoard.ts:130`）；
3. 「修改 / 补充」的显示条件是 `['SUBMITTED','APPROVED'].includes(status)`（`:183-234` / `:237-271`）；
4. `REJECTED` 不落在任何一侧→ **三个入口同时关闭**，且全代码库无 `REJECTED → CLAIMED` 的回退路径。

**违反的参考流程**：你明确要求「组织者/悬赏者可驳回重新至提交方案」。
**影响面**：悬赏闭环最关键的一条回路断掉；认领人无法自救，只能私聊组织者。

### 🔴 BUG-02【P0】`POST /api/state/reset` 无鉴权，可一键清空全库

**复现**：`curl -X POST https://.../api/state/reset -d '{"by":"x"}'` → `200 已清空服务端数据`

**实测影响**：我在 L1 探健康时误调此接口，**本地库被真清空**（已从 `server/data/state.json.bak-*` 恢复；线上 version 184 未受影响，已核实）。

**根因假设**：`server/index.mjs` 的 reset 分支既未校验 `X-WB-Token`，也未校验调用者角色。
**额外风险**：即使配了免登，`/api/state/reset` 仍是「谁都能调」——它绕过了整套数据面鉴权。
**建议**：① 立即加角色校验（仅 ORGANIZER/ADMIN）；② 生产环境直接关闭该端点；③ 或至少要显式 `confirm` token。

### 🟠 BUG-03【P1】悬赏方案审核：发布者无入口 + 组织者无回避校验

**与参考流程不一致**：你要求「方案待**组织者/悬赏者**审核」，实际只有 `/admin/bounty` 一条路。

| 项 | 系统实际 | 参考要求 |
|---|---|---|
| 审核人 | 仅 ORGANIZER/ADMIN（`auth/access.ts:69-73`） | 组织者 **或** 悬赏发布者 |
| 自己发布的悬赏能否自审 | `approveSolution` **缺 `owner !== me` 校验**（`BountyReview.tsx:154`） | 应回避（同页发布审核处有 `disabled`，方案审核处没有） |

**根因假设**：方案审核复用后台统一入口，未区分「谁的悬赏」；两条审核路径的校验强度不一致。

### 🟠 BUG-04【P1】v2 悬赏详情可见性判断缺取反符（v1/v2 行为不一致）

`src/pages/v2/BountyListV2.tsx:270-272` 条件为 `... && me.roles.includes('ORGANIZER')`，**缺 `!`**；
v1（`src/pages/c/BountyList.tsx:252-256`）正确。

**现象**：组织者访问 `PENDING_REVIEW` / `REJECTED` 的悬赏详情时，**v2 判为「当前对外不可见」，v1 正常**。
**影响**：v2 默认启用 → 组织者审悬赏时可能看不到待审内容（或与v1 表现相反）。
**根因**：照搬 v1 代码时漏了取反。

### 🟠 BUG-05【P1】`dist/` 累积 59 个历史 chunk、66MB

**现象**：`npm run build` 后 `dist/assets/` 有 59 个 JS（多个 1.8MB 的同内容旧版本），总计 66MB。
**根因**：`vite.config.ts` 设`emptyOutDir: false`（为规避批量删除被沙箱拦截），导致历史产物永不清理。
**影响**：部署包体积虚增（虽只上传当前 index，但归档/备份会持续膨胀）。
**建议**：部署脚本里加一步「只保留本次构建的产物」的白名单清理（不用 `rm -rf`）。

---

### 🟡 BUG-06【P1】自动推送评委总闸默认关闭，且无推送记录实体

`pushSettings.autoPush` 默认 `false`（`src/store/store.tsx:82`），`runSubmitPipeline` 在关闭时直接 `continue`（`submitPipeline.ts:518`）。

**现象**：不手工开启 → 第 5 环「推送评委」**静默跳过**，不产生任何消息，用户以为推了其实没有。
**附带**：没有独立的「推送记录」实体，只有 status + messages 间接体现，无法回答「这条推给谁过、什么时候推的」。

---

### 🟡 BUG-07【P1】评委队列不校验「是否推送给本人」

`src/pages/b/JudgeReview.tsx:81-86` 的 `baseQueue` 只按 `status ∈ [AI_SCORED, REVIEWING, REVIEWED, SPOT_CHECK]` 过滤 + 排除自己。

**与参考流程不一致**：你要求「组织者统一推送至评委进行复核」，隐含**评委只看被推给自己的**。
实际：**评委看到全部该状态作业**。
**根因**：推送时写了 `MSG-JDG-*` 消息，但评分队列没用这个归属关系做过滤。

---

### 🟡 BUG-08【P2】补充资料：审核人看不到正文

`SolutionSupplement[]` 只 push 不改状态（设计正确，符合你「不修改原方案」的要求），入口在悬赏卡片/详情的「补充资料」按钮。
但**审核页只显示「补充 N」标签**（`BountyReview.tsx:136-146`），**看不到补充正文与附件** → 组织者无法核验补充内容。

---

### 🟡 BUG-09【P2】下架（OFFLINE）的悬赏仍出现在大厅

大厅过滤条件为 `status ∉ {MEMBER_DRAFT, PENDING_REVIEW, REJECTED}`（`useBountyBoard.ts:62-66`），**未含 OFFLINE**。
**现象**：组织者下架后，悬赏仍在大厅展示且可点「认领」。

---

### 🟡 BUG-10【P2】`EXPIRED` 状态无自动流转 + `campaign_id` 硬编码

- `EXPIRED`（48h 超期释放）**全代码无任何写入/定时器**，只存在于文案与后台按钮 → 实际不会自动发生；
- 悬赏积分入账时 `campaign_id` **硬编码 `'C2026Q4'`**（`BountyReview.tsx:67-77`）→ 跨活动结算风险。
